# NeoSync 0.1.0-beta.9

Minecraft **1.21.1**, NeoForge **21.1.256**, Java **21**. Published beta.8 assets
and its tag retain their original bytes and identity.

On a real beta.8 server, selected valid NeoForge JARs failed metadata inspection
with `Alternative loaders and loader service providers are not supported`.
Minecraft continued running without the NeoSync status field, so the client
continued into ordinary gameplay login before reviewing the missing mods.

The correction accepts supported NeoForge archive arrangements generally:
merged loader metadata, declared recursive JarJar libraries, language bundles,
optional JarJar fields, multi-release libraries and case-distinct resources.
Inspection remains bounded and does not execute classes. Unsupported loader
services, unsafe paths, class aliases and incompatible dependency sets remain
rejected. No mod names select special behavior.

Schema 2 records the effective client mod inventory chosen by NeoForge's JarJar
selector while retaining metadata and hashes for each enclosing artifact.
Clients recompute the selection before publishing or verifying a prepared
profile. Shared embedded versions do not become separate downloads. Legacy
schema 1 remains readable; beta.8 clients reject schema 2, so install the matching
candidate on both client and server.

The server creates sibling `mods_client` for client-only JARs that cannot load on
a dedicated server. Every file there is classified CLIENT without a side
question. It supplements the existing inventory, proposes client selection and
respects saved exclusions. Exact sources, provider restrictions, administrator
review, client consent, hashes and isolated profiles retain their existing flow.
This directory does not authorize serving third-party JARs directly.

New configurations use `"enabled": true`. Existing configuration bytes,
including an explicit disabled choice, are preserved. Failed enabled discovery
advertises unavailability and produces a client startup error instead of an
automatic ordinary connection.

## Validation before official CI

- Formatting, compilation and installer/source packaging passed locally.
- 236 NeoSync Linux unit tests passed with the candidate universal and scratch
  JUnit runner, including symbolic-link rejection, metadata, effective dependency
  selection, profile transactions and enabled defaults. Official CI still checks
  the complete project through its normal Gradle classpath.
- 119 of 120 selected Windows tests passed. The remaining existing
  symbolic-link test could not create its fixture with the current Windows
  privileges; the same test passed on Linux.
- The exact local installer installed and started a dedicated Windows server,
  created `mods_client` and an enabled configuration, and shut down cleanly.
  A second start on an available local listener port enabled discovery. The
  first default-port attempt encountered an existing listener on port 8443.
- Read-only analysis of the real VPS's 65 selected JARs verified their metadata,
  exact sources and required client dependencies: 82 active mod IDs, 64
  Modrinth files and one CurseForge file. This used authorized beta.8 access
  with the candidate inspection classes; it was not a deployed endpoint.
- Package inspection passed for embedded libraries, versioned paths, source
  identity, branding and unchanged FML code.

Local candidate packages omit CurseForge access. Official CI must build and
validate the authorized package before VPS deployment or client delivery.
Custom language services still receive FML's normal validation when the profile
boots. The real VPS boot with this candidate and native SKlauncher remote
download/restart/gameplay remain pending; metadata analysis alone does not
establish those results.

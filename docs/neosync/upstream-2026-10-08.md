## Additional launcher work

The previous implementation already identified SKlauncher and Modrinth but
offered manual guidance only. This change reuses the existing official profile
writer for SKlauncher 3.2 and adds native runtime import and per-server instance
creation for SKlauncher 4.0 Beta and Modrinth. The new standalone graphical
installer installs the runtime and registers each launcher automatically. It
displays original icons, detected paths, disabled missing folders and a custom
folder selector. Users need Java 21, with no Python steps. Windows packaging
embeds the exact installer JAR in an EXE and verifies extraction and Java discovery.
See [launcher setup](launchers.md).

The source installation is retained so FML uses the generated client and
NeoSync universal JAR from the verified installer. Classpath/module libraries
are copied into the launcher's own library tree and checked against the installed
metadata's size and SHA-1. Prepared instance game arguments select the original
verified profile path. No mod files, markers, manifests or consent records are
relocated. Accounts are not copied, selected, queried or logged.

Launcher preparation requires the existing separate consent action. It validates
the selected profile before creating anything and rejects edited target runtime
metadata. JSON inventory edits use staging, concurrent-change checks and atomic
rename. Modrinth registration uses a bounded-lock SQLite transaction and rolls
back on errors. Unknown database schemas require a compatible app version;
no migration of the launcher's database is attempted.

These integrations keep the existing verification on startup. Prism alone retains
the separately implemented pre-launch verifier and automatic CLI handoff. Launching
Minecraft through the other adapters requires selecting the prepared instance and
pressing Play; full installed multiplayer acceptance is not implied by format tests.

## Validation

Checks ran on Windows 11 amd64 with Eclipse Adoptium Java 21.0.12.1:

- `applyAllFormatting`, `checkFormatting`, compilation and `git diff --check`
  passed. Python setup syntax and repeat imports passed.
- All nine standalone installer tests passed: existing profile/account-fixture
  preservation, missing targets, corrupt libraries, edited metadata, SKlauncher
  compatibility mode, idempotency, Modrinth overrides and transactional rollback.
- The graphical installer was opened on Windows with original launcher icons and
  the existing Prism directory detected. The user reviewed and approved its UI.
  Later visual automation was interrupted; no additional visual acceptance is
  claimed for those attempts.
- The final Windows EXE passed embedded JAR SHA-256 verification, Java 21 discovery
  and the SQLite/installer self-test. It completed a full automatic client install
  into a fresh custom folder containing spaces with exit code zero. The JAR also
  completed an automatic official-launcher installation into a separate test root.
- Java adapters imported the final installed runtime into fresh Prism, SKlauncher
  Beta and Modrinth test roots containing spaces. Each repeated without duplicate
  instances or changed records. The Modrinth test used schema definitions only.
- The full initial unit run executed 292 tests: 282 passed and ten pre-existing
  tests failed while creating symbolic links because this Windows process lacks
  that privilege. After the additional rollback regression, the final run passed
  all 283 executable tests, using a scratch init script to exclude exactly those
  ten methods. They are excluded from execution, not validated or counted as passing.
  All five launcher integration tests passed, including edited runtime/instance
  rejection, cancellation, preservation, and unsupported database rollback.
- Both native setup routes imported an actually installed runtime into separate
  test roots with spaces, preserved personal-instance/account fixtures, rejected
  edited metadata, and repeated without duplicate instances. Modrinth registration
  used the installed app's table definitions (schema only, no account data), and
  `PRAGMA foreign_key_check` returned no violations. New instance sync preferences
  remained disabled.
- The final installer installed and started the graphical client and dedicated
  server through the repository's production harness, writing both self-test
  reports and exiting cleanly. The final run passed without a scratch init script:
  the build now maps `serverLauncher` directly from its destination directory,
  fixing the existing Gradle task-provider evaluation error.
- Separate graphical production-harness runs of the fully merged SKlauncher Beta
  and Modrinth metadata reached the client self-test with their native library trees
  and an isolated game directory containing spaces. These runs validate imported
  runtime startup, not the launchers' own argument parsers, account UI or Play flow.
  Modrinth's whitespace behavior and override handling were confirmed in its source.
- Installer metadata contains SQLite JDBC 3.46.1.3 and the matching FML, Mixin and
  branded early-display versions. Archive inspection found no account files or
  optional provider credential resource. Minecraft game directories and test
  worlds remain local and are not delivered.
- Release validation passed with the exact Windows EXE and its embedded installer,
  matching universal/early-display JARs, source identity, branding and FML 4.0.45
  code compared with pristine upstream archives. Workflow YAML parsed successfully.
- **Accept all** replaces the installation acceptance label for the full reviewed
  mod set. The specific source warning remains a separate default-negative action.
  The installed acceptance driver's button lookup follows the new label; a fresh
  multiplayer run for this label-only change was not performed.

Actual SKlauncher 3.2, SKlauncher 4.0.54 and Modrinth UI multiplayer acceptance
remains pending. The installer supports the default combined inventory/runtime
layout; separately relocated data directories require manual activation. These
adapters require selecting the instance and pressing Play, and retain post-load
profile verification. They do not inherit Prism's pre-launch verification or
automatic restart guarantees. Historical September 29 and published release checks
remain in their existing documents and are not reassigned to this source revision.
